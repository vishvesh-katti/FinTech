================================================================================
0.0  PHILOSOPHY & GUIDING PRINCIPLES
================================================================================

RetailQuant Pro applies institutional quantitative frameworks to the retail
Indian user's personal cash flow. The market is crowded with passive aggregators
(INDmoney, Walnut) that show users what already happened. RetailQuant Pro shows
users what will happen, under what probabilities, and exactly how to change it.

FOUR CORE COMMITMENTS (derived from Remediation Plan):

  1. NO DEAD ENDS — Every failure state (0% probability, impossible goal,
     API failure) must resolve into a guided alternative action. The UI
     never leaves a user stranded with a number and no path forward.

  2. RUPEE-ANCHORED LANGUAGE — All risk, returns, and projections are
     expressed in actual ₹ amounts tied to the user's parsed data.
     Abstract percentages (1-5 scales, "Debt allocation") are always
     accompanied by plain-English translations.

  3. HONEST MATH — Deployable surplus is calculated conservatively with
     all lock categories. Projections use GBM with jump diffusion, not
     straight-line compounding. The engine will tell the user a plan is
     broken before suggesting they open a brokerage account.

  4. GRACEFUL DEGRADATION — Every API call (yfinance, Claude, RBI) has
     a fallback. A stale data warning is always preferable to a crash or
     a fabricated error message shown to the user.

TARGET DEMOGRAPHIC:
  Urban Indian professionals, age 25–45, income ₹5L–₹50L annually.
  Pain points: cash drag, subscription bloat, poorly constructed MF
  portfolios, and zero downside protection during market corrections.

1.0  SYSTEM ARCHITECTURE
================================================================================

DESIGN PATTERN: Decoupled 6-stage pipeline. Each stage computes independently
and passes a clean schema to the next. Heavy quantitative work (optimisation,
Monte Carlo) is isolated in backend modules, never blocking the UI thread.

1.1  FRONTEND LAYER
  - Framework       : Streamlit 1.35+
  - Theme           : "Institutional Dark" — custom CSS injected globally
                      (Navy #0A0F1E, Electric Blue #00D4FF, Gold #FFD700,
                       Coral #FF6B6B for warnings, Green #00FF88 for positive)
  - Charting        : Plotly Express + Graph Objects exclusively.
                      No default Streamlit charts anywhere.
  - Layout          : Custom sidebar with 6-stage progress tracker.
                      Expandable sections for information density management.
                      Glassmorphism metric cards. Animated number counters.
  - State           : st.session_state — all user data ephemeral in-session.

1.2  BACKEND & DATA PROCESSING
  - Language        : Python 3.10+
  - Data            : pandas, numpy, scipy
  - Market Data     : yfinance (primary, 2Y/1H granularity — see §6)
                      Local CSV fallback cache for all 12 assets.
  - AI Engine       : Anthropic Claude 3.5 Haiku API (categorisation only)
  - Optimisation    : scipy.optimize.minimize (Sharpe maximisation)
  - Simulation      : NumPy vectorised GBM (10,000 paths)
  - Caching         : @st.cache_data, TTL=4 hours for market data

1.3  PRIVACY & SECURITY
  - Ephemeral only  : No database. Session destroyed on tab close.
  - PII Scrub       : Regex strips names, UPI IDs, account numbers before
                      any string reaches the Claude API endpoint.
  - No telemetry    : No analytics SDK. No third-party tracking.

2.0  STAGE 1 — DATA INGESTION & INTELLIGENT VALIDATION
================================================================================

2.1  SUPPORTED INPUT FORMATS
  a) CSV  — Standard Indian bank exports (SBI, HDFC, ICICI, Axis, Kotak,
             Yes Bank, IndusInd). Auto-detected via header heuristics.
  b) PDF  — Bank statement PDFs parsed via pdfplumber with table extraction.
  c) JSON — API-connected users (future). Validated against unified schema.

2.2  COLUMN NORMALISATION ENGINE
  Scans first 10 rows. Maps bank-specific headers to unified schema:
    "Debit" / "DR" / "Withdrawal Amt" / "Debit Amount" → withdrawal
    "Credit" / "CR" / "Deposit Amt" / "Credit Amount"  → deposit
    "Narration" / "Description" / "Particulars"        → narration
    "Value Date" / "Txn Date" / "Transaction Date"     → date
    "Balance" / "Closing Balance" / "Avl Bal"          → balance

  MERGED AMOUNT COLUMN HANDLING:
  Some banks export a single "Amount" column with +/- signs. The loader
  splits this into separate withdrawal/deposit columns automatically.

  UNIFIED OUTPUT SCHEMA (12 columns):
  [date, narration, withdrawal, deposit, balance, bank_name,
   account_masked, statement_start, statement_end, currency,
   is_duplicate_flag, outlier_flag]

2.3  DATA INTEGRITY ENGINE
  a) Duplicate Detection  : Same date + amount + narration within 24h window.
  b) Balance Reconciliation: Rolling computed balance vs. stated balance.
                             Discrepancy > ₹100 triggers a warning flag.
  c) Temporal Gap Analysis : Flags gaps > 5 consecutive calendar days.
                             Gaps > 30 days lower the Data Confidence Score.
  d) Outlier Flagging      : Transactions > 3 standard deviations from the
                             user's own mean flagged for manual review.
  e) ATM/Cash Detection    : "ATM WDL" pattern isolated as "Untracked Spend."
                             High ATM usage lowers Data Confidence Score.

2.4  DATA CONFIDENCE SCORE (0–100)
  Starts at 100. Deductions:
    - Statement covers < 3 months              : −30 points
    - Balance reconciliation discrepancy found : −15 points
    - Temporal gap > 30 days found             : −10 points per gap (max −20)
    - ATM cash withdrawals > 20% of outflows   : −15 points
    - Duplicate transactions found             : −5 points per group

  Displayed as a gauge to the user with explanation of each deduction.
  Scores < 50 trigger a persistent banner: "Low data quality may reduce
  projection accuracy. Consider uploading a longer or more complete statement."

2.5  OUTPUT
  Clean, normalised pandas DataFrame with 12 standardised columns.
  Passed to Stage 2 via st.session_state["clean_df"].

PHASE A — LOCAL CACHE LOOKUP (Cost: ₹0, handles ~65% of volume)
  - Check narration against merchant_cache.json (pre-seeded with 500+
    common Indian merchants: Swiggy, Zomato, Amazon, BSNL, HDFC EMI etc.)
  - Regex pattern library (e.g., "*SWIGGY*", "UPI/9876*", "NEFT-SALARY*")
  - TF-IDF similarity against cached narrations (threshold: cosine > 0.88)
  - If confidence >= 0.88: assign category, skip API call. Cache the result.

PHASE B — CLAUDE API ROUTING (Only for ambiguous transactions)
  - Batch all unresolved narrations in groups of N=20.
  - PII scrub before sending: strip names, UPI IDs, account numbers.
  - System prompt forces JSON-only output (no preamble, no markdown fences).
  - Retry logic: 3 attempts with exponential backoff (1s, 2s, 4s).
  - On API failure after 3 retries: assign category="Uncategorised",
    confidence=0.0. Do NOT crash. Show warning badge in UI.
  - Cache every successful response to merchant_cache.json for this session.

  System: "You are a financial transaction categoriser for Indian bank

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4A.  FINANCIAL HEALTH SCORE (0–850, credit-score style)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SIX SCORING DIMENSIONS (weighted, totalling 100%):

  1. SAVINGS RATE (25%)
     Monthly savings ÷ Monthly income.
     <10% → 0 pts | 10–20% → 150 pts | 20–35% → 175 pts | >35% → 212 pts

  2. DEBT SERVICE RATIO (20%)
     Total EMIs ÷ Monthly income.
     <20% → 170 pts | 20–35% → 100 pts | >35% → 30 pts

  3. EXPENSE DIVERSIFICATION (15%)
     Herfindahl-Hirschman Index (HHI) on spending category percentages.
     HHI = Σ(share_i²). Lower = more diversified = higher score.
     HHI < 0.20 → full score. HHI > 0.50 → 0 pts (concentrated risk).

  4. INCOME STABILITY (15%)
     Coefficient of Variation (CV) of monthly income credits.
     CV < 0.05 (very stable salary) → full score.
     CV > 0.30 (freelancer with volatile income) → 0 pts.

  5. INVESTMENT ACTIVITY (15%)
     SIP/MF/investment transactions detected? Yes → full score.
     No investment activity → 0 pts for this dimension.
     Bonus: +10 pts if investment-to-income ratio > 15%.

  6. EMERGENCY FUND ADEQUACY (10%)
     Current estimated liquid balance vs. (3× to 6× monthly fixed expenses).
     Fund ≥ 6 months → full 85 pts.
     Fund 3–6 months → 50 pts.
     Fund < 3 months → 0 pts.

OUTPUT DISPLAY:
  Circular Plotly gauge (0–850) with colour gradient.
  Letter grade: A+ (750+) / A (650–749) / B (500–649) / C (350–499) / F (<350)
  Score Improvement Roadmap: exactly 3 specific, data-driven steps to move
  the score up by at least 50 points, e.g.:
    "Start a ₹5,000/month SIP. This alone adds +127 points to Investment Activity."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4B.  DEPLOYABLE SURPLUS CALCULATION — 5-LOCK SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Formula:
  DEPLOYABLE SURPLUS = Current Liquid Balance − (Lock A + Lock B + Lock C +
                                                  Lock D + Lock E)

LOCK A — Fixed Obligations Reserve (exact, from AI categorisation)
  = Σ all transactions where is_fixed=true × 1 month buffer
  Includes: rent, EMIs, insurance premiums, fixed subscriptions.

LOCK B — Dynamic Variable Reserve (personalised, not flat 15%)
  = Average monthly variable spend × (1 + CV_discretionary)
  Where CV_discretionary = coefficient of variation of discretionary spend
  over the statement period. High-volatility spenders get a larger buffer.
  Minimum multiplier: 1.15. Maximum: 1.40.

LOCK C — Emergency Fund (personalised, not static ₹25,000)
  = 3× average monthly fixed expenses (minimum lock)
  = 6× average monthly fixed expenses (recommended lock)
  For freelancers (CV_income > 0.20): always use 6× figure.
  Shown to user as a range, not a single number.

LOCK D — Tax Liability Reserve
  If self-employed signals detected (GST, professional receipts):
    = Estimated advance tax installment (30% of net surplus, conservative)
  If salaried with TDS detected: Lock D = 0.

LOCK E — Short-Term Goal Reserve (user-defined)
  User optionally tags upcoming large expenses (holiday, gadget, wedding).

6A.  MARKET DATA FETCH — 2Y/1H SPECIFICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FETCH COMMAND (data_fetcher.py):
  ticker_obj = yf.Ticker(ticker)
  df = ticker_obj.history(period="2y", interval="1h")

WHY 2Y/1H:
  • 2 years captures at least one full market cycle (bull + correction).
  • 1-hour bars give sufficient resolution for EMA crossover signals and
    intraday volatility patterns without the noise of 1-minute data.
  • yfinance supports 1h interval up to 2 years reliably (730 days max
    for hourly; beyond that falls back to daily auto).
  • For quantitative metrics requiring daily close (CAGR, MaxDD, Sharpe),
    hourly data is resampled to daily OHLCV using:
      daily_df = hourly_df.resample('B').agg({'Open':'first','High':'max',
                  'Low':'min','Close':'last','Volume':'sum'}).dropna()

CACHING:
  @st.cache_data(ttl=14400)  # 4-hour cache
  All 12 assets fetched in a single parallelised batch at stage entry.
  On fetch failure: load from data/fallback_prices/<ticker>_2Y_1H.csv.
  Fallback CSV is updated manually and shipped with the app.

GRACEFUL DEGRADATION (REMEDIATION):

6C.  METRICS COMPUTATION (from 2Y/1H data, resampled to daily)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FROM DAILY RESAMPLED CLOSE (for each of 12 assets):

  RETURN METRICS:
  • CAGR (2Y, 1Y, 6M) — show trend direction
  • Annualised return (geometric mean of daily returns × 252)
  • Best Month / Worst Month (range of human experience)
  • Maximum Drawdown = max(1 - P_t / cummax(P)) over the 2Y window

  RISK METRICS:
  • Annualised Volatility = std(daily_returns) × √252
  • Sharpe Ratio = (CAGR − 0.065) ÷ Ann_Volatility
    (Risk-free rate hardcoded at 6.5% = approx 91-day T-bill)
  • Sortino Ratio = (CAGR − 0.065) ÷ Downside_Deviation
    Downside deviation = std of returns below 0 × √252
  • Beta vs. ^NSEI = Cov(asset_returns, nifty_returns) / Var(nifty_returns)
  • VaR (95%, parametric) = mean_daily − 1.645 × std_daily
    Displayed as: "In a bad month, you could lose up to X%"

  FROM 1-HOUR DATA (regime and momentum signals):
  • 50-hour EMA (fast) and 200-hour EMA (slow) for each asset
    These are equivalent to 50-day and 200-day EMAs at hourly resolution,
    giving more responsive crossover detection within Indian trading hours.
  • Rolling 24H realised volatility (detects intraday vol spikes)
  • Hurst Exponent (on hourly Nifty 50 returns) — see §6D

  CORRELATION MATRIX:
  Full 12×12 Pearson correlation matrix on daily log-returns.
  Displayed as Plotly annotated heatmap (colour scale: -1 red → 0 white → 1 blue).
  Used downstream for Marchenko-Pastur denoising.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6D.  MARKET REGIME DETECTION — HURST EXPONENT + DUAL EMA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SIGNAL 1: HURST EXPONENT (on hourly Nifty 50 log-returns, 2Y window)

  Formula (Rescaled Range analysis):
    For time window τ:
      R(τ) = max(cumulative deviations) − min(cumulative deviations)
      S(τ) = std dev of the τ-length sub-series
      E[R(τ)/S(τ)] = C × τ^H
    H is estimated by log-log regression of R/S vs. τ across multiple windows.

  REGIME ROUTING:
    H < 0.45  → Mean-Reverting / Choppy
                UI flag (amber): "Market is trendless. Avoid lump-sum. Use
                Systematic Transfer Plan (STP) over 3–6 months."
                Action: hold 20% extra in LIQUIDBEES; queue weekly STP tranches.

    0.45–0.55 → Random Walk
                UI flag (neutral): "Market is range-bound. Execute baseline
                allocation per risk profile."

    H > 0.55  → Trending / Persistent
                UI flag (green): "Market is trending. Greenlight lump-sum
                equity deployment."
                Action: Full equity sleeve deployed immediately.

SIGNAL 2: DUAL-ADAPTIVE EMA CROSSOVER (on daily close, per equity asset)

  EMA Formula:
    α = 2 / (N + 1)
    EMA_t = α × P_t + (1 − α) × EMA_{t−1}

  Tracking:
    Fast EMA = 50-day (derived from daily resampled close)
    Slow EMA = 200-day (200-day moving average = full 2Y window avg)

  BEAR SIGNAL triggered when BOTH conditions are true simultaneously:
    (1) Fast EMA crosses below Slow EMA (death cross)
    (2) Current price < 200-day EMA (confirms downtrend, prevents whipsaws)

  ACTION on Bear Signal:
    Reduce recommended equity allocation by 50% for that specific asset.
    Reallocate the freed weight: 50% → LIQUIDBEES, 50% → GOLDBEES.

  COMBINED REGIME OUTPUT (4 states, rule-based):
    BULL     : Nifty above 200D EMA, H > 0.50, no death cross on major indices
    FROTHY   : Nifty above 200D EMA, H > 0.55, PE > 25 (hardcoded threshold)
    BEAR     : Death cross confirmed on Nifty + price below 200D EMA
    RECOVERY : Price just crossed above 200D EMA from below (buying signal)

  CONTEXTUAL ADVISORY SHOWN (example for FROTHY):
    "Markets are currently extended. Nifty PE at ~X. Consider deploying via
     STP rather than lump sum. At current Gold/Nifty ratio, gold looks
     relatively attractive as a tactical hedge."

STEP 2 — MARCHENKO-PASTUR COVARIANCE DENOISING

  WHY: Raw empirical covariance matrices contain noise eigenvalues. Optimising
  against noisy covariances leads to "error maximisation" — overweighting
  statistical artifacts as if they were real diversification signals.

  MATHEMATICS:
    Q = T / N  where T = number of daily observations (~504), N = 12 assets
    σ² = 1 (normalised correlation matrix)
    λ_max = σ² × (1 + √(1/Q))²    ← maximum noise eigenvalue threshold

  EXECUTION:
    1. Compute empirical correlation matrix C from daily log-returns.
    2. Eigendecompose: C = V Λ V^T  (eigenvalues λ₁ ≥ λ₂ ≥ … ≥ λ₁₂)
    3. Identify noise set: {λᵢ : λᵢ ≤ λ_max}
    4. Replace noise eigenvalues with their mean (preserves matrix trace).
    5. Reconstruct denoised correlation matrix: C̃ = V Λ̃ V^T
    6. Convert to covariance matrix: Σ̃ = D^(1/2) × C̃ × D^(1/2)
       where D = diagonal of annualised variances.

STEP 3 — SHARPE MAXIMISATION (scipy.optimize.minimize)

  Objective: Maximise Sharpe Ratio = (w^T μ − r_f) / √(w^T Σ̃ w)
    Where μ = vector of 12 asset annualised CAGRs (from 2Y data)
          Σ̃ = denoised covariance matrix
          r_f = 0.065 (risk-free rate)
          w = portfolio weight vector

  CONSTRAINTS:
    Σ wᵢ = 1.0         (fully invested)
    wᵢ ≥ 0              (no short positions)
    MaxDD(w, historical_returns) ≤ MaxDD_tolerance (from Stage 4 risk profile)
    wᵢ ≤ profile_upper_bound[i]  (per-asset cap from base allocation × 1.5)

  BLEND: Final_w = 0.60 × base_profile_w + 0.40 × optimised_w
  This prevents a pure black-box quant allocation that users won't trust.

STEP 4 — REGIME OVERLAY (Dual-Adaptive Momentum)
  Apply bear signals from §6D:
  For each equity asset flagged with a death cross:
    Final_w[equity_asset] × 0.50 → reallocate to LIQUIDBEES + GOLDBEES

  For Hurst < 0.45 (mean-reverting regime):
    Cash Equivalents sleeve bumped to min(current + 15%, 30%).
    Equity reduced proportionally. STP flag set = True.

STEP 5 — HORIZON TILT
  Goals < 3 years  : Shift 20% weight from equity → Fixed Income + Liquid.
  Goals 3–7 years  : No additional tilt.
  Goals > 7 years  : Shift 10% weight from Fixed Income → equity (time diversifies).
  Multi-goal blend : Weighted average tilt by (capital_per_goal × horizon_weight).

STEP 6 — TAX EFFICIENCY OVERLAY

7A.  DETERMINISTIC SCENARIO ENGINE (3 scenarios, per goal)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For each goal, three deterministic projection paths are computed:

  BEAR CASE   : Each asset CAGR = historical_2Y_CAGR − 1.0 × ann_volatility
                Label: "Pessimistic (Bad Decade)"

  BASE CASE   : Each asset CAGR = historical_2Y_CAGR
                Label: "Expected (Historical Average)"

  BULL CASE   : Each asset CAGR = historical_2Y_CAGR + 0.5 × ann_volatility
                Label: "Optimistic (Strong Decade)"

  Portfolio CAGR for each scenario = Σ(wᵢ × CAGRᵢ_scenario)

  OUTPUTS per scenario:
  - Year-by-year corpus table (expandable section, Indian number format)
  - Final corpus vs. goal target (₹ gap or surplus, colour-coded)
  - Inflation-adjusted real value of final corpus at goal date
  - % probability of hitting goal (derived from Monte Carlo, §7B)

  LUMP SUM vs. SIP COMPARISON:
  Both paths shown on the same Plotly line chart per scenario.
  Annotation: "In a trending market (H > 0.55), lump sum historically
  outperforms SIP over a 7-year horizon. In choppy markets, SIP wins."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7B.  MONTE CARLO SIMULATION ENGINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MODEL: Geometric Brownian Motion with Merton Jump Diffusion overlay.

GBM MATHEMATICS:
  dS_t = μ S_t dt + σ S_t dW_t

  Discretized monthly formula:
    S_{t+1} = S_t × exp((μ − σ²/2) × Δt + σ × Z × √Δt)
    Where Z ~ N(0,1), Δt = 1/12 (monthly step)
    μ = portfolio_expected_cagr (from §6E output)
    σ = portfolio_volatility

JUMP DIFFUSION OVERLAY (Merton approximation):
  Each monthly step: draw U ~ Uniform(0,1)
  If U < (0.05/12):  ← 5% annual probability, distributed monthly
    Inject jump shock: S_{t+1} × (1 + jump_size)
    jump_size drawn from Uniform(−0.30, −0.15)  ← −15% to −30% shock
  This models Indian market fat tails and crash events.

VECTORISED EXECUTION (10,000 paths):
  paths = np.zeros((10000, N_months + 1))
  paths[:, 0] = initial_corpus
  Z = np.random.standard_normal((10000, N_months))
  jump_mask = np.random.uniform(0,1,(10000,N_months)) < (0.05/12)
  jump_sizes = np.random.uniform(-0.30,-0.15,(10000,N_months))
  for t in range(N_months):
      paths[:, t+1] = paths[:, t] × exp(drift × Δt + σ × Z[:,t] × √Δt)
      paths[:, t+1] × np.where(jump_mask[:,t], 1+jump_sizes[:,t], 1.0)
  (SIP contributions added monthly: paths[:, t+1] += monthly_sip)

PROBABILITY OF SUCCESS:
  success_count = Σ(paths[:, −1] >= goal_target)
  probability_of_success = success_count / 10000

CHART — PROBABILITY FAN CONE (Plotly):
  5 percentile bands plotted:
    10th pct (worst 10%) — thin coral band
    25th pct             — medium amber band
    50th pct (median)    — white bold line
    75th pct             — medium green band
    90th pct (best 10%)  — thin electric blue band
  Goal target shown as a dashed horizontal gold line.
  Shaded area between 25th and 75th = "Most Likely Range."

REMEDIATION — NO DEAD ENDS:
  If probability_of_success < 80%:
    DO NOT show a static number and leave the user stranded.
    Auto-generate 3 resolution suggestions displayed in a coral panel:
      "Option 1: Extend timeline by [N] years → success probability rises to ~Y%"
      "Option 2: Increase monthly SIP by ₹[X] → probability rises to ~Y%"

A1. YFINANCE 2Y/1H KNOWN LIMITATIONS
  - yfinance hourly data is returned for the last 730 calendar days maximum.
  - Weekend and holiday bars are absent (expected, handle with dropna()).
  - GOLDBEES and SILVERBEES may have volume=0 on thin trading days — handle
    with forward-fill for price, zero for volume.
  - Global equity (CSPX.L) returns in USD. Apply daily INR=X close price
    to convert all returns to INR-equivalent before metrics computation.
    inr_rate = yf.Ticker("INR=X").history(period="2y", interval="1d")["Close"]

A2. SCIPY OPTIMISER NOTES
